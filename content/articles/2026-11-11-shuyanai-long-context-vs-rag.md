# 用数眼智能 API聚合平台做资料助手：长上下文与 RAG 怎么选

2026-11-11｜技术路线对比与项目讨论

> 本文由 AI 辅助整理，结合公开资料讨论立项、实施和维护，未开展在线性能、费用或安全测试。下文的售后资料助手为假设项目，不对应真实客户或交付经历。

设想一家企业准备做售后资料助手。资料里有现行手册、旧型号说明，还有后来补发的服务规则。员工提问时，希望知道某个型号目前适用什么规定，并能打开原文核对。

第一版怎么做，团队很可能会出现两种想法：把本次有关的资料整理好，一并交给支持相应上下文长度的模型；或者先建检索流程，找到相关段落，再让模型回答。后一种做法通常称为检索增强生成，也就是 RAG。

两种办法都能列出一份技术清单。但这个项目真正要避免的，是引用过期规则、把相近型号混在一起，或者回答中有链接，打开却找不到对应依据。选型应围绕这些结果展开。

在数眼智能 API聚合平台上选择模型，只是其中一层。资料怎么整理、谁可以访问、更新后如何替换旧内容，仍然需要项目自己的安排。

## 立项：先确定要回答的问题，再数文件

文件数量适合做资料盘点，却不足以单独决定技术路线。几份手册也可能包含复杂表格和互相修订的条款；一个较大的资料库，也可能每次只围绕已知型号的一份手册提问。

对这个假设项目，可以先请售后负责人整理几类问题：明确型号的参数查询、需要同时阅读两个章节的问题、新旧规则冲突的问题，以及资料中根本没有答案的问题。每个问题都应标出适用版本、必要证据和需要追问的条件。

例如，“这个设备能否适用新规则”缺少型号或购买时间时，项目可能要求先补充信息。这个要求应在立项时确定，不能只靠后来调整提示词，期待模型自行理解业务边界。

人工整理的这组问题，是两条路线共同的比较依据。除了回答是否正确，还要检查依据是否完整、人工修改多少，以及没有依据时是否按要求停下来。先把什么结果可以交付说清楚，再讨论索引、模型和数据库，技术工作才有方向。

## 技术路线：直接读资料与先检索，各多承担哪一步

本文所说的“直读”，是把经过权限筛选和整理的本次资料放入模型上下文，不预先建设专门的检索索引。RAG 则先从资料集合中找出相关内容，再把它们作为回答依据。检索可以采用关键词、向量或组合方式，不必把 RAG 等同于某一种数据库。

| 比较项 | 长上下文直读 | 检索后再生成（RAG） |
| --- | --- | --- |
| 资料怎样进入模型 | 由应用选定本次需要的资料，组成输入 | 先检索候选资料，再选取内容组成输入 |
| 先要解决的事 | 资料能否放入、结构是否清楚、模型能否正确使用 | 该找哪些内容、能否找全、片段是否保留必要上下文 |
| 可能遗漏在哪里 | 材料已给出，但模型忽略了条件或混淆版本 | 正确证据没有进入候选内容，或筛选时被丢弃 |
| 更新涉及什么 | 更新资料源和组装输入的版本，处理相关缓存 | 更新资料源、索引和相关缓存，并核查检索结果 |
| 运行记录关注什么 | 实际输入范围、模型输出和引用依据 | 检索候选、最终输入、模型输出及其对应关系 |

直读省去的是预建检索索引这项工作，资料整理和答案核对仍然存在。RAG 增加了找证据的步骤，有机会缩小每次提交的内容范围，也增加了检索、更新和排错工作。能否改善效果或总投入，要放回相同任务中比较。

上下文长度也不等于资料使用能力。2023 年的《Lost in the Middle》研究在其测试模型与任务中观察到，相关信息的位置会影响表现。这是一项历史研究，不能直接用来给当前模型打分，但提示项目在验证时改变证据位置、加入干扰资料，而不是只试一次容易回答的问题。[研究原文](https://arxiv.org/abs/2307.03172)

RAG 同样有自己的短板。Anthropic 的 Contextual Retrieval 技术文章讨论了切片失去原文背景后影响检索的问题。对于售后手册，项目可以保留型号、章节、版本与适用条件，检查片段离开整页后是否仍然表达完整；具体切分与检索设置需要自己的样本验证。[技术说明](https://www.anthropic.com/research/contextual-retrieval)

这两条路线也可以组合。例如，先确定用户有权访问且型号匹配的手册，再把完整相关章节交给模型。先缩小资料范围与使用较长上下文，解决的是不同环节的问题，不必在立项时把它们设成永久二选一。

## 实施：先查资料是否读对，再查答案是否有依据

同样一份手册，如果表格中的单位丢失，或者型号与对应参数在提取后错位，两条路线都可能受到影响。实施时应先抽查原文件与提取内容，尤其关注表头、脚注、修订说明和跨页条件。

数眼智能公开产品页分别介绍了搜索、网页解析和 OCR，接口资料也提供当前 Key 的模型查询。这些可以作为资料处理与模型接入的研究入口，但不能据此认定平台已经替项目完成私有知识库、权限同步、版本索引和答案验收。[搜索](https://www.shuyanai.com/products/search)、[网页解析](https://www.shuyanai.com/products/extraction)、[OCR](https://www.shuyanai.com/products/ocr)、[模型与接口文档](https://doc.shuyanai.com/doc-8652765)

模型能否处理本次输入，还要单独确认上下文、输出预留空间、输入格式和账户权限。出现在模型列表里，不代表具备项目要求的全部长文本能力。扫描文档经过 OCR 后能读出文字，也不等于原来的表格关系已经准确保留。

资料准备好之后，再用同一批问题比较两条路线。尽可能固定生成模型、版本、提示要求和输出标准，分别记录实际输入。若无法确认模型对应关系，就保留这个差异，不把结果当成严格的同条件比较。

对 RAG 路线，排错可以顺着证据走：

- 预期证据没有被找到，先检查资料是否进入索引，以及检索、过滤和排序规则。
- 正确片段已经交给模型，但回答漏掉限制条件，再检查片段完整性、提示要求和生成行为。
- 回答内容大体正确，引用却对不上，则检查出处映射和引用展示，不能仅凭存在链接判定通过。

直读路线也应保存本次组装的资料清单与版本。否则回答出了问题，团队无法分清是没有放入正确文件，还是文件已在输入中却没有被正确使用。

权限判断要发生在资料进入模型之前。直读时只组装本次获准使用的材料；RAG 则需要将用户权限应用到检索与内容选择，并在提交前核对最终片段。把无权访问的内容先交给模型，再要求它不要回答，不能作为资料访问控制。

## 验收：用会让系统为难的问题比较

顺利找到一条参数，能说明基本流程可用。要决定是否上线，还需要检查有歧义、冲突和缺失的情况。下面是这份假设项目可以采用的验收样本类型，并非本文已执行的测试。

| 样本情况 | 希望观察到的行为 |
| --- | --- |
| 相近型号使用不同参数 | 依据指定型号回答；型号不清楚时按约定追问 |
| 旧手册与补发规则并存 | 依据预先确认的版本关系处理冲突，不能任意拼接 |
| 答案需要两个章节共同支持 | 保留两处证据，避免只回答其中一半 |
| 资料里没有所问结论 | 说明依据不足，进入约定的补充资料或人工流程 |
| 用户没有某份资料的访问权 | 该内容不进入本次模型输入，也不出现在可见引用中 |

不同路线可以各自调整到合理状态，再用保留的问题集复核，避免一边反复优化、另一边只跑默认设置。开发投入也要一起记录，才能看清取得某个结果需要付出什么工作。

成本则按完整流程核对。两条路线都要记录实际发生的资料解析、模型调用、重试、人工复核和维护投入，并把费用与人工时间分列。RAG 另外核对索引、检索、重排等环节；没有使用或已被套餐覆盖的项目，按实际情况注明，避免遗漏或重复计算。没有这些数据，不宜仅凭输入片段更短就认定 RAG 一定更省。

具体费用记录可以接着使用[项目账本文章](2026-11-08-shuyanai-api-cost-reconciliation.md)中的方法，本篇不代填平台报价或节省比例。

## 维护：一条规则更新后，旧答案还会从哪里出现

假设资料助手已经试用，售后负责人又补发了一条新规则。对直读方案，要检查权威资料源、输入模板和缓存是否仍带入旧版本；对 RAG 方案，还要查看旧片段是否退出当前可用范围、新内容是否进入索引，以及查询能否找到它。

源文件被替换，不代表所有派生内容已经同步改变。片段、索引、答案缓存和历史会话可能保留旧内容。哪些历史记录只供追溯、哪些内容仍能参与新回答，需要事先约定。文件撤销或权限收回时，也应复核这些路径。

团队可以让资料负责人确认生效版本与适用范围，由开发或维护人员处理发布和索引，再让业务人员复查受影响的问题。小团队可以一人兼任，但更新是否完成，要以新查询行为和记录为依据。

模型变更也需要回到问题集验证。资料没变，回答仍可能随模型或参数改变；检索方式变了，也要检查原先能找到的证据是否还在。保留配置与资料版本，有助于定位变化发生在哪一环。

这时再回看立项的选择，会更接近项目实际。如果每次涉及的资料都很明确，且验证结果满足要求，可以继续使用当前直读流程；如果人工挑资料已经成为负担，或者多种查询需要从大集合里找证据，就有理由进一步评估检索。是否扩展，由遇到的问题决定，不用给文件数量设一个通用分界线。

## 选型前容易问到的几个问题

**长上下文够大，是不是就不用做 RAG？**

还要看资料范围、任务效果、权限和更新成本。放得下只是条件之一；也可以先筛选资料，再使用较长上下文。

**做了 RAG，回答是不是就有依据了？**

还需要确认找到了正确证据、证据进入了输入，回答与引用也确实受到它支持。检索结果的存在不能代替这几项核对。

**用了数眼智能的搜索和解析工具，就算知识库交付完成了吗？**

这些工具可以承担资料获取或处理中的部分步骤。私有资料组织、访问控制、版本管理、索引与应用验收，需要按实际方案落实。

**第一版可以先直读，之后再加检索吗？**

可以作为分阶段方案讨论。早期保留文档标识、版本、出处和验证问题，会为后续调整留下基础；如果立项时就有明确的大范围检索需求，也应提前验证。本文讨论的两套流程均不是仓库现有客户端已经实现的功能。

对这个假设的售后资料助手，第一步是拿出能够核对依据的回答。接着观察挑资料、找证据和更新内容分别花了多少工作，再决定把哪些环节交给检索。模型接入、资料治理和业务验收放在同一条流程里比较，技术路线才有持续调整的依据。
