# 数眼智能 API聚合平台字段抽取对比：JSON 输出与工具参数怎么选

2026-11-16｜数据契约与字段接收方案

> 本文由 AI 辅助整理，结合官方文档与标准资料讨论方案，未进行在线调用或字段抽取实测。采购清单整理为假设案例，示例字段不属于真实订单。

录入系统要的是“数量、单位、物料编号”，模型却返回一句“建议订购十二箱”。文字能够理解，但接收程序还不知道该把哪个值放进哪一列。把回答改成 JSON，或者让模型返回一组工具参数，都可以作为接收结构化数据的方式。

假设一个团队要把获准使用的采购清单整理为待审核草稿。这里先不讨论自动下单，也不让工具调用直接改变业务数据。要比较的是：两种返回方式怎样与同一份字段契约衔接。

## 先写契约，再选择承载形式

字段契约至少要说清名称、类型、必填规则、允许取值、单位，以及缺失和冲突怎样表示。例如，数量采用数值，单位另列；没有可靠物料编号时填待核状态，不从商品名称中猜出一个编号。

JSON Schema 的官方说明区分了属性定义、必填项和额外属性处理。只在 `properties` 中列出字段，并不等于这些字段已经必填；是否允许额外字段也应明确设置。[对象约束说明](https://json-schema.org/understanding-json-schema/reference/object)

这份契约属于接收系统，不能只存在于提示词里。将来换模型或换返回方式时，接收端仍应按约定检查，避免把接口适配变化扩散到业务数据中。

## 两种返回方式的差别

| 比较内容 | JSON 输出 | 工具参数抽取 |
| --- | --- | --- |
| 数据放在哪里 | 按接口和模式约定读取回答中的结构 | 按工具调用结构读取目标函数的参数 |
| 接收端先检查什么 | 是否完整、能否解析、是否符合目标结构 | 工具是否匹配、调用数量、参数能否解析及结构 |
| 与业务动作的关系 | 可仅用于生成待审数据 | 也可仅作为字段承载，不必执行真实业务动作 |
| 需要明确的异常 | 截断、缺字段、额外内容、类型不符 | 未调用、调用了其他工具、多个调用或参数不符 |

如果目标只是接收一份数据，JSON 路线可以围绕这份结构设计处理逻辑。如果应用本来就通过工具调用协议交换类型化请求，工具参数路线也可以纳入验证。两者都需要按目标模型核对实际行为，不能预先认定某一种天然更准。

## “合法 JSON”与“符合契约”是两次检查

一个结果即使能解析为 JSON，也可能把数量写成字符串、漏掉单位，或者增加接收系统不认识的字段。第一步解析成功后，还要按契约检查类型、必填项、枚举和额外属性。

工具参数也要经过相同检查。看到熟悉的函数名称，不能跳过参数解析；一次返回多个候选调用时，也不能默认取第一个。项目应提前约定期待一份数据、多个条目，还是允许模型先说明信息不足。

随后才是字段与原始材料的对应。例如，清单写的是“每箱十二件，计划三箱”，数量字段究竟表示箱数还是件数，需要业务定义。Schema 可以约束类型，却无法仅凭一个整数确定它忠实表达了材料含义。

接收端应当能说明每个字段为何通过、为何待核。为待审记录保留来源片段和字段状态，可以帮助经办人员逐项核对。

## 做一组能够暴露接口差异的样本

可以准备字段齐全、缺少单位、两种数量表达并存、存在未知物料，以及根本不是采购清单的输入。先由业务人员给出预期结构和可接受的待核状态，再让两种方案处理相同材料。

记录分成几层：收到完整响应没有，载体能否解析，契约检查是否通过，字段是否对应材料，以及是否被经办接受。不要把这些状态压成一个成功标记，否则无法分清问题发生在模型响应还是接收系统。

对 JSON 路线，可测试回答夹带说明、响应截断和字段类型变化。对工具参数路线，可测试没有目标调用、多个目标调用及未知参数。测试工具只是验证环境中的数据接收器，不承担提交订单等业务操作。

两边都应允许“无法确定”。如果契约强迫每个字段都有一个看似确定的值，模型可能用推断填补原文缺失；如果所有字段又都可省略，接收程序也无法判断是没有信息还是漏提取。缺失原因应进入状态设计。

## 契约升级，才是后续协作容易卡住的地方

假设后来需要新增“包装规格”。直接改变旧字段含义，可能使旧记录仍能通过检查却被错误理解。更稳妥的项目安排是给契约版本留出位置，写明旧、新数据怎样识别，什么时候停止接收旧结构。

提示词、工具定义和接收校验应一起发布，并保存对应版本。否则模型按新规则输出，后端却仍按旧规则解析，问题会被误判成模型不稳定。

人工修正记录也应回到样本中。经办人员把“十二箱”改成“十二件”时，需要说明是原文读错、单位约定不清，还是实际业务变更。不同原因对应的改动位置不一样。

如果应用最后需要执行提交，授权、业务条件和重复操作保护应在另一层实现。通过字段契约仅表示数据满足约定结构，不等于用户已经同意该动作，也不证明业务接口执行成功。

## 两个常见疑问

**工具参数看起来像函数，是否必须执行它？**

不必把字段接收自动连接到业务写入。可以先把参数作为候选数据解析、校验并展示为草稿，后续按项目约定处理。

**用了 JSON Schema，是否可以减少人工核对？**

它能帮助表达和检查结构约束，减少多少人工工作仍需实际记录。原文含义、单位和业务事实不会因格式通过就自动得到确认。

这份假设清单项目可以让两条路线共用同一契约、同一批样本和同一种待核状态，再比较适配工作与实际接收结果。返回形式只是入口，字段含义和版本规则应掌握在应用自己手里。
