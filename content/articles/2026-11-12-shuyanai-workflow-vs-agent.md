# 用数眼智能 API聚合平台做业务应用：固定工作流与 Agent 怎么选

2026-11-12｜业务自动化路线对比与项目讨论

> 本文由 AI 辅助整理，依据公开资料讨论方案，未开展在线性能、费用或安全测试。订单协同项目及对话均为假设，不对应真实客户或交付经历。

“帮我看看这单为什么还没发，能改地址的话，再告诉我怎么处理。”

设想商家准备给客服做一个订单协同助手。这句话里既有查询，也有条件判断，还可能涉及修改信息。系统要找到正确订单，理解当前状态，区分可以解释的内容和允许执行的操作，最后给客服一份可以核对的结果。

开发团队于是面临一个选择：把步骤和分支提前编排好，还是让模型根据工具返回的信息决定下一步？用数眼智能 API聚合平台接入模型之后，这个应用层的选择仍然存在。

今天沿着这个假设项目，比较固定工作流与 Agent。重点放在控制方式、交付条件和后续维护，不比较概念听起来有多先进。

## 立项：先决定交付到哪一步

这个订单助手的第一版，可以只做“查询信息并生成处理建议”，也可以进一步承担“按业务规则提交修改”。两种目标对状态管理、权限和验收的要求不同，立项时应当分别写清楚。

如果第一版只给客服草稿，就要核对订单状态是否准确、建议有没有依据、人工还需要补充哪些信息。如果计划真正修改业务数据，还要明确哪些用户可以操作、什么条件下可以执行、是否需要进一步确认，以及结果未知时由谁接手。

已有明确授权且条件满足的常规步骤，可以按约定执行；需要补充信息、权限不足或情况发生变化时，应停在相应节点。不能只用“由人复核”四个字带过，因为复核的是建议、参数，还是已经发生的操作，会影响整条流程。

立项材料可以从典型任务开始整理：单纯查状态、订单号不清楚、信息相互矛盾、条件不满足，以及提交后没有收到明确结果。先约定这些任务怎样算完成，再讨论模型能自主决定多少步骤。

## 技术路线：区别在谁决定下一步

固定工作流可以包含模型、工具和条件分支。Agent 也可以受预算、权限和业务规则约束。为了便于比较，本文采用一种控制方式上的区分：工作流由程序安排主要路径，Agent 在允许范围内依据中间结果选择后续动作。Anthropic 在其 2024 年工程文章中也采用了类似区分；这里引用的是概念定义，不涉及当前框架或托管产品的功能比较。[工程文章](https://www.anthropic.com/research/building-effective-agents)

| 比较项 | 固定工作流 | 由模型选择后续工具的 Agent |
| --- | --- | --- |
| 路径怎样确定 | 开发者定义步骤、分支与跳转条件 | 模型在允许的工具和操作范围内选择后续步骤 |
| 遇到新情况 | 看是否有对应分支，没有时进入约定的补充或人工流程 | 可以尝试组合已有工具，但能否处理仍需验证 |
| 验证重点 | 分支条件、步骤衔接和异常路径 | 工具选择、参数、停止判断及整段执行过程 |
| 成本记录 | 记录实际经过的步骤和调用 | 除单次调用外，还需关注循环次数与不同任务路径 |
| 维护对象 | 流程定义、模型提示、工具与业务规则 | 同样需要维护模型和工具，还要检查规划与停止行为 |

对于“查询订单—检查发货状态—生成解释”这类边界比较明确的任务，可以把主要路径直接写出来。模型仍可负责理解表达和组织说明，不必因为流程固定就放弃自然语言能力。

如果任务需要根据情况追加查询，例如先判断是拆单、库存等待还是物流信息延迟，再选择对应的查询工具，可以评估让 Agent 参与这部分调查。前提是这些工具确实可用，执行范围清楚，而且新增的灵活性通过了样本验证。

两种方式可以放在同一项目里：外层工作流负责身份、任务状态和提交规则，某个调查步骤允许 Agent 使用只读工具，回到明确的结果格式后再继续。这样的安排也需要验证，但不必把整项业务都交给一个没有边界的循环。

## 实施：模型提出工具调用，应用负责落实执行

工具调用需要把模型侧与业务侧的职责分清。模型可以生成工具名称与参数，真正读取订单、修改信息的，是应用连接的业务系统。调用请求是否合法、当前用户有没有权限、参数是否满足业务条件，都应在执行端检查。

本次可检索到的数眼智能聊天文档（v2.2.0）描述了这样的工具流程：模型返回 `tool_calls`，客户端执行函数后，将对应工具结果回传，再请求模型继续处理。工具调用请求与实际执行结果，需要分别记录。[聊天接口的工具调用说明](https://doc.shuyanai.com/doc-8784048)

模型查询文档则说明了当前 Key 的可调用范围。对本项目而言，还要进一步确认目标模型与接口是否满足所需工具调用方式，不能只凭列表里出现了模型，就认定整套 Agent 流程已经具备。[模型与接口文档](https://doc.shuyanai.com/doc-8652765)

实现时，可以先把订单查询、物流查询和提交修改设计成不同工具。给模型的工具说明写清用途、必要参数、返回状态与常见失败情况。只读工具与会改变业务状态的工具分别管理，应用也不必在每次任务里向模型开放全部工具。

模型返回一个看起来正确的工具调用，不代表动作已经完成。应用应校验参数和权限，执行获准动作，保存业务系统的结果，再决定如何继续。最终向客服展示的状态，也需要能对应到这些记录。

例如，业务系统没有明确返回修改成功时，助手应保留“结果待确认”的状态。模型给出“已经帮您处理好”的文字，不能补上缺失的业务证据。

这类状态区分对固定工作流和 Agent 都适用。程序预先安排了步骤，也可能在步骤之间超时；模型能够继续推理，也不能靠猜测得知外部操作是否成功。

## 验收：检查过程，而不只看最后一句话

对同一批订单协同任务，两条路线可以记录相同的结果：是否识别了正确订单、信息是否足够、采取了什么动作、实际状态怎样，以及没有完成时是否进入约定的处理流程。

下面是这个假设项目可使用的样本类型，不是本文已执行的测试。

| 样本情况 | 应检查的结果 |
| --- | --- |
| 缺少订单标识，或者匹配到多个订单 | 先澄清或按业务规则处理，不自行猜一个订单 |
| 查询结果表明已不满足修改条件 | 保留当前事实，不以继续调用代替条件判断 |
| 外部文本夹带与任务无关的操作指令 | 按数据处理，不改变应用授权范围和提交规则 |
| 提交后超时，实际结果未知 | 查询业务状态或转入接手流程，不直接重复提交 |
| 已达到调用、时间或费用边界 | 按预设方式停止，保留已有进度和未决事项 |

工作流要覆盖分支与异常路径；Agent 还要检查为什么选了某个工具、是否反复查询同样的信息、证据不足时能否停止。两边都应看业务任务的完成情况，不能只用一次工具调用成功来代替项目验收。

对于会改变状态的动作，重复执行尤其需要设计。AWS Builders' Library 的技术文章讨论了请求超时后重试可能产生额外副作用，以及通过接口幂等约定处理重复请求的方法。这是服务端与客户端配合的机制，不能由模型提示词单独保证。[重试与幂等 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

落到订单助手，应核对业务接口实际支持什么：是否有可复用的业务操作标识、怎样查询已提交结果、重复请求会得到什么响应。仅在本地写了一条“已发送”日志，不足以证明对方已经完成，也不能保证再次提交不会产生第二次修改。

费用比较也以同一业务目标为准。模型调用、工具服务、重试、人工接手和维护投入都按实际情况记录；Agent 的路径可能变化，工作流也可能因多次模型调用产生不同投入。没有这些记录，就不把某一种方式写成固定更省或更快。

## 维护：任务中断后，谁能把它接下去

设想助手已经查到订单状态，提交修改时却断开了连接。第二天系统恢复，客服又打开同一个任务。此时最有价值的信息是：之前查到了什么、提交过什么、业务系统有没有确认，以及还剩哪些事情没有解决。

任务记录应能区分“准备执行”“已经发出”“结果已确认”和“结果未知”等状态，并保存关联的业务标识。恢复执行前，先检查外部实际状态，再判断从哪里继续。把历史对话重新发给模型，不能代替这一步核对。

这不是 Agent 特有的问题。固定工作流也需要安排状态保存、重复处理和人工接手。采用哪种运行方式，都应明确这些能力由框架、应用服务还是业务系统承担，不能因为用了某个接口就默认全部存在。

维护时还要留意工具和规则变化。订单字段、修改条件或权限改变以后，原先正确的参数和步骤可能已经不适用。工作流要检查分支与衔接，Agent 则还要重看工具说明、模型选择和执行轨迹。

当模型、提示、工具定义或执行策略调整时，可以用保留的任务集复测，并记录版本。日志应帮助定位问题，同时按需要脱敏，不把完整凭证或无关的客户信息长期混在调试记录里。

如果客服已经花很多时间修正同一种调查步骤，可以针对那一段重新设计；如果任务一直很固定，也没有必要为了形式上成为 Agent 而增加决策循环。是否扩展，由实际任务和维护记录推动。

## 项目推进时，可以带着这些问题作决定

| 阶段 | 决定前要说清楚的事 |
| --- | --- |
| 立项 | 交付建议还是执行动作，哪些条件必须满足，谁接手未完成任务 |
| 路线验证 | 哪些步骤可以提前确定，哪些确实需要根据中间信息再决定 |
| 实施 | 模型负责什么、执行端检查什么、业务系统怎样返回和保存结果 |
| 验收 | 正常与异常任务能否得到可核对的结果，停止和恢复是否符合约定 |
| 维护 | 哪些变更需要复测，记录保存在哪里，故障与结果未知时由谁处理 |

数眼智能 API聚合平台的模型接口，可以作为这套应用的模型接入部分。流程编排、业务权限、执行状态、重试和人工接手，则要按实际方案分别落实。本文讨论的工作流与 Agent 均为设计方案，仓库现有客户端没有实现这些业务运行能力。

## 常见问题

**用了工具调用，就已经是 Agent 吗？**

不一定。固定流程也能调用工具。本文关注的是后续路径主要由预设程序控制，还是由模型在允许范围内根据结果选择。

**工作流里能不能只放一小段 Agent？**

可以作为组合方案验证。需要明确这一段的输入、可用工具、预算、停止条件和输出格式，以及回到外层流程后的处理方式。

**接口返回结束了，业务就完成了吗？**

要分别看模型响应、工具执行与业务系统结果。只有符合项目约定的结果和状态，才能作为业务完成的依据。

**第一版怎样控制投入？**

先用代表性任务验证需要哪些步骤，把调用、工具和人工工作分别记录。对已经能明确表达的路径，不必预先增加自主循环；有实际变化需求的步骤，再比较其他安排。

对这个假设的订单助手，项目可以先把查询和建议做扎实，再按明确的业务条件扩展执行能力。真正影响路线选择的，是任务是否需要灵活调查、动作能否被约束、结果能否确认，以及出问题后有没有人能够接手。
