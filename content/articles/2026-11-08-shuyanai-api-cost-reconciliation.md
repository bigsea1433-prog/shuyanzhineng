# 数眼智能 API聚合平台费用核对：从 Token 用量到项目账本的资料分析

> **公开资料分析与应用侧设计讨论**  
> 发布及资料核验日期：2026-11-08。本文由 AI 辅助整理，依据公开文档分析费用记录方法，未使用真实 API Key 查询账户或开展付费测试。文中的金额与任务记录均为虚构演示，不代表平台报价、客户账单或实际效果。

一个项目完成了三次写作任务，后台却出现四次调用记录，费用应该怎样核对？关键在于把业务任务、实际调用和金额来源分别记录，再建立对应关系。一次任务可能重试，也可能调用多个模型和工具；用户最终看到一份结果，不能说明只发生一次消耗。

本文接着[接口与计费口径分析](2026-11-06-shuyanai-api-aggregation-review.md)，讨论怎样建立应用侧的费用记录。本次不比较平台价格高低，也不根据公开接口判断账单准确率。

## 一、先明确查询对象和计量单位

数眼智能当前文档把兼容查询接口的粒度标为 **Key 级**，不能将其中一个 Key 的结果直接视为整个账号或项目的支出。字段口径还需要分别核对：

| 文档中的字段或接口 | 本次核验的说明 |
| --- | --- |
| `billing/subscription` 的额度字段 | `soft_limit_usd` 等以人民币元表示，名称中的 `usd` 为兼容命名 |
| `billing/usage` 的 `total_usage` | 当前 Key 的累计消费，单位为人民币分 |
| `start_date`、`end_date` | 兼容保留参数；传入后仍返回累计值，不按日期筛选 |
| 密钥配置的 `remain_quota` | 内部额度单位，与人民币元、分分别处理 |

来源：[额度与用量查询文档](https://doc.shuyanai.com/doc-8652765)、[密钥管理文档](https://doc.shuyanai.com/doc-9218823)。

因此，做每日统计不能只改查询日期，也不能把“总额度”“剩余额度”“累计消费”放在同一列求和。记录时应同时保存数值、单位、查询对象和采集时间；展示时再按明确规则换算，并保留原始精度。

## 二、把一次任务拆成可追溯的调用尝试

下面是本文提出的应用侧记录方案，不是平台已有账单字段，也不代表本仓库已经实现这套系统。

| 记录内容 | 用途 |
| --- | --- |
| 项目标识、业务任务标识 | 判断费用属于哪个项目、哪次业务操作 |
| 调用尝试标识 | 每次实际发送请求分别编号，区分首次调用与重试 |
| Key 内部别名、请求模型、返回模型及分组 | 对应调用配置，未返回的字段标为未知；不存完整密钥 |
| 开始、结束时间及时区 | 核对统计窗口和跨日任务 |
| 请求结果与业务结果 | 区分接口返回、连接中断和输出是否被采用 |
| 上游返回标识与用量原值 | 有返回时保留；缺失时明确标为未知 |
| 金额、金额来源和确认状态 | 区分估算、已匹配记录与待核实项 |

例如，用户点击一次“生成摘要”，可以分配一个任务标识。第一次请求超时后决定再发一次，应新增调用尝试记录，保留前一次状态；不能用第二次成功结果覆盖第一次记录。

记录本身重放或重复写入时，可按应用自建的调用尝试标识去重。但去重只针对重复记录：如果确实又发送了一次请求，就需要保留第二次尝试，不能因为提示词相同而删除。本地记录去重也不能证明上游支持请求幂等，或保证重试不产生额外费用。

业务结果也需要独立保存。模型正常返回，但内容不符合要求或被人工弃用，仍是一次已经发生的调用，不能从费用分析中排除。

## 三、Token、估算费用和已确认金额分列保存

聊天响应中的 `usage` 描述模型用量，不是最终金额。文档对推理用量也有特定口径：`completion_tokens` 包含推理 Token，不能把其中的推理明细再次加到输出总量上。[聊天响应与用量说明](https://doc.shuyanai.com/doc-8784048)

若要根据用量估算费用，需要明确当时适用的模型、价格版本、计费单位和规则。数眼智能密钥文档还说明分组对应可用模型及计费倍率；只记录模型名称，可能不足以解释不同配置下的估算差异。[分组说明](https://doc.shuyanai.com/doc-9218823)

应用可以将金额状态分成三类：

- **估算：** 根据已知用量及明确的计费规则计算，保留价格依据与时间。
- **已匹配：** 已与另行取得的明细或服务方确认记录对应，注明来源。
- **待核实：** 用量、适用规则或金额来源不足，暂不填入确定金额。

估算结果后续得到确认时，应更新同一笔记录的状态，或用明确的冲销、替代关系处理，避免把估算和确认金额累计两遍。平台是否提供所需粒度的明细、如何取得和如何匹配，需要另行确认；本文未验证明细导出能力。

## 四、虚构例子：三次任务，四次调用，差额怎样保留

**以下数字全部用于演示，单位为人民币分，不是平台价格或真实账单。** 假设同一个 Key 在两个采集时点的累计消费分别为 `10000` 和 `10180`，差值为 `180` 分，即 `1.80` 元。

同时，假设应用通过另行取得的记录，已匹配到下列金额：

| 业务任务 | 调用尝试 | 应用观察到的结果 | 已匹配费用（分） |
| --- | --- | --- | --- |
| T1 | T1-A1 | 返回并采用结果 | 40 |
| T2 | T2-A1 | 等待超时，处理状态未知 | 未知 |
| T2 | T2-A2 | 再次请求后返回结果 | 60 |
| T3 | T3-A1 | 返回结果，内容未采用 | 30 |

已匹配金额合计为 `40 + 60 + 30 = 130` 分，与累计差值之间还相差 `50` 分。此时应记录“差额 50 分待核实”，不能直接把它归到 T2-A1，也不能因为超时就将那次请求记为零费用。

核对时需要检查：是否还有其他应用共用此 Key，是否遗漏调用，采集窗口是否一致，以及是否存在尚未反映在记录中的调整或更新。本文没有验证累计接口的更新延迟或调整机制，应先确认实际规则，再解释差异。

T3 虽然没有被采用，已匹配费用仍保留。这样可以分别计算“接口调用投入”和“获得可用结果的投入”，不会只留下成功案例。

## 五、累计快照能帮助发现差异，不能自动分摊到项目

对同一个 Key，两个累计采集值之差，可以作为这段采集窗口内的消费变化观察值。使用前需要确保查询对象、单位和口径一致，并记录边界时刻；它不自动等于准确的自然日账单，也不能单凭一个差值归因到某次请求。

多人或多个项目共用 Key 时，累计变化还可能包含其他调用。如果一个项目更换过 Key，统计也需要覆盖对应的使用时间段，并处理切换期间的并行请求。Key 的别名和所属项目映射可以保存在应用配置中，避免直接依赖易变的显示名称。

采集失败应保留空缺。后续恢复采集后，即使得到较长时间段的累计差值，也不能在没有依据时平均分配到缺失的每一天。如果累计值回退，或查询对象、单位发生变化，应暂停按差额归账并核对原因。退款、冲正或其他调整如果存在，也应单列记录，不能当成新的模型输出。

## 六、超时与流式中断时，保留“未知”状态

客户端超时只能说明没有按时拿到完整结果，不能单独证明上游未处理或不会计费。继续发送请求前，应结合业务是否允许重复生成、已有记录和当前规则作决定。

聊天文档提供流式用量返回选项；启用 `stream_options.include_usage` 时，最终用量块的 `choices` 可以为空。解析程序应独立处理用量块，避免只读取正文而漏掉统计。[流式响应说明](https://doc.shuyanai.com/doc-8784048)

如果连接提前中断，没有收到最终统计，应记录“用量未收到”，不能把缺失字段转换为零。接口返回正常、文本完整、用量齐全和金额已确认，是四个不同状态，可以分别检查。

## 七、FAQ

### 传入某一天的日期，就能查询当天费用吗？

按本次核验的兼容查询规则，不能这样使用。期间核算需要适用的明细，或明确边界与限制的累计快照记录。

### 一个业务任务只需要记一笔吗？

可以保留一条任务汇总，但实际请求应逐次记录，汇总时包含重试及未采用结果。

### 请求失败可以直接记零元吗？

不能仅凭失败提示作判断。先标记结果和金额状态，再依据可核对记录确认。

### 可以将搜索、阅读和模型费用全部按 Token 相加吗？

应先确认每类服务的单位、计费规则及统计范围。不同计量方式分别记录，在核对后再汇总，不能假定全部包含在一个模型用量字段中。具体规则以适用产品说明和订单为依据。[服务与计费范围说明](https://www.shuyanai.com/terms-of-service)

### 本仓库的客户端已经实现自动对账了吗？

没有。[现有示例](../../examples/README.md)覆盖模型列表和非流式文本调用。本文讨论的任务账本、累计快照、流式统计与费用匹配，是应用侧设计方案。

## 资料分析结论

费用核对需要同时回答三个问题：发生了哪些调用、每条记录采用什么计量口径、金额由什么证据确认。公开接口文档能说明部分字段与查询范围，完整的项目记录还需要应用自己的任务关联和异常处理。

保留估算与确认金额的区别、失败尝试和未解释差额，可以为后续排查提供具体线索。本文不据此判断平台价格、收费准确性或实际节省效果。
