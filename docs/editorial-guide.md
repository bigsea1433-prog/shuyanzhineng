# 用 GitHub 网页持续写文章

这个仓库把文章放在 `content/articles/`，把文章目录放在 `content/README.md`。日常写作可以直接使用 GitHub 网页，无须安装编程工具。

## 发布第一篇文章

1. 打开仓库中的 `templates/article.md`，复制模板正文。
2. 回到仓库首页，点击 **Add file → Create new file**。手机或较窄窗口可能将操作收进菜单。
3. 在文件名中输入完整路径，例如 `content/articles/2026-11-06-first-api-call.md`。使用英文短文件名，正文和标题可以写中文。
4. 粘贴模板，写好标题、日期、正文、资料来源和核验日期。把占位文字替换掉。
5. 切换 **Preview**，检查标题、列表、代码块和链接是否正常。
6. 点击 **Commit changes…**，填写简短说明，例如“新增：数眼智能接入实践”。个人仓库可按页面提供的选项直接提交到默认分支；如选择新建分支，则继续创建并合并 Pull request 后，文章才会进入默认分支。
7. 打开 `content/README.md`，点击铅笔图标编辑，新增一条文章链接，再保存提交。

文章目录中的链接示例：

```markdown
- [数眼智能接入实践](articles/2026-11-06-first-api-call.md) — 2026-11-06
```

这里的链接相对于 `content/README.md`，所以以 `articles/` 开头。

## 修改已经发布的文章

打开文章，点击铅笔图标进入编辑；完成后先预览，再提交。提交说明写具体变化，例如“修正模型列表接口说明”，方便以后查找。文章末尾可以增加一条更新记录，说明重要事实何时调整。单纯修正标点不必另写更新记录。

若页面没有编辑按钮，请先确认已登录仓库所属账户，或具有该仓库的写入权限。不要为了改一篇文章创建或公开访问密钥。

## 草稿、命名与目录

- **正式文章：** `content/articles/YYYY-MM-DD-topic.md`，如 `2026-11-06-api-basics.md`。
- **草稿：** `drafts/YYYY-MM-DD-topic.md`，标题旁标明“草稿”，确认后再放入正式文章目录。
- **文章模板：** `templates/article.md`，每次新文章复制一份。
- **文章索引：** `content/README.md`，每发布一篇就添加链接，建议新文章放在前面。
- **附图：** 可放在文章旁的 `assets/` 目录，使用清楚的文件名，并注明图片来源。

公开仓库中的 `drafts/` 也能被别人看到。未公开的商业资料、个人信息和账户凭据应保留在本地或适当的私有空间。

## 每篇文章的写法

围绕一个具体问题展开，例如“怎样完成第一次聊天请求”或“聚合接口出现超时怎么处理”。推荐按“问题—公开资料—自己的设计或操作—验证结果—适用边界”组织正文。代码放在代码块中；长篇代码优先链接仓库里的示例文件，避免文章和代码分别更新后不一致。

可以持续写以下主题：

1. 首次接入：配置入口、密钥和模型名称。
2. 写作应用：提纲、摘要与修改建议的任务拆分。
3. 平台设计：模型适配、超时、限流与错误分类。
4. RAG 实践：搜索、网页阅读和来源引用。
5. 评估记录：同一组任务的效果、耗时和实际费用。

## 发布前核对事实与来源

- 产品功能与接口优先引用官方页面，并记录核验日期。旧文章中的参数不保证今天仍有效。
- 清楚区分“官方文档说明”“作者设计建议”和“实际测试结果”。没有运行过的例子写明尚未实测。
- 不编造价格、可用率、响应速度、客户案例、授权关系或官方身份。比较结果需说明测试时间、任务和条件。
- 引用公开代码前检查具体仓库的许可证；能够浏览的代码不等于可以任意复制。引用原文用短引文并附链接，正文用自己的话解释。
- 不上传真实 API Key、令牌、Cookie、账单截图或含客户信息的日志。示例使用环境变量和占位值。
- 检查目录链接能否打开，文件名与链接是否一致，预览里是否还有未替换的占位内容。

## 关于文章网页

Markdown 文章提交后即可在 GitHub 仓库内阅读和分享。GitHub Pages 是另外一种网站发布方式；本指南不假定它已经开启。先用仓库目录持续写作即可，如以后需要独立的文章网站，再单独配置站点与发布流程。
